An experiment must produce knowledge, not just executable code

This October 2025 practice essay distinguishes developer agents from experimenter agents. A developer produces a software artifact; an experimenter must support a valid conclusion. The authors argue that stateful notebooks improve iteration and inspectability, while emphasizing optimistic reporting, hidden shortcuts, and human validation as persistent problems. Their examples and task suite provide directional experience rather than a rigorously audited benchmark of autonomous research.

Prerequisites: reproducible computation and hypothesis testing and controls. An experiment specifies a question, intervention or measurement, comparator, and interpretation rule. Provenance records which data, code, model state, and execution produced each result. Stateful execution retains objects between commands; this accelerates work but can make results depend on hidden execution history.

Original teaching case: throughput can move the bottleneck

Let agents produce candidate experiments at rate $\lambda$ and a reviewer validate them at rate $\mu$, both in experiments per hour. In a simple queue with independent exponential service and arrival times, steady-state utilization is $\rho=\lambda/\mu$, requiring $\lambda\lt\mu$. The expected number waiting is

$$L_q=\frac{\rho^2}{1-\rho}.$$

Let $N$ be the stationary number of experiments in the system, including one under review. Adjacent-state balance gives $P(N=n+1)=\rho P(N=n)$, hence $P(N=n)=(1-\rho)\rho^n$ for $n\geq0$ when $\rho\lt1$. The geometric-series identity $\sum_{n=0}^\infty\rho^n=(1-\rho)^{-1}$ gives $\sum_{n=0}^\infty n\rho^n=\rho/(1-\rho)^2$ by differentiation and multiplication by $\rho$. Therefore $\mathbb{E}[N]=\rho/(1-\rho)$. The reviewer is busy with probability $\rho$, so the expected number waiting is $\mathbb{E}[N]-\rho=\rho^2/(1-\rho)$.

This is an illustrative M/M/1 queue model, not a measurement from the essay. At $\lambda=4$ and $\mu=5$, $\rho=0.8$ and $L_q=3.2$. At $\lambda=4.9$, the same reviewer faces $L_q=48.02$. Increasing generation near review capacity creates a large backlog even though every individual experiment is cheap. Real review times need not be exponential, but the capacity constraint remains.

Multiple testing creates a second scaling problem. If 20 independent null hypotheses are each tested at significance level $0.05$, the probability of at least one false positive is $1-0.95^{20}\approx0.6415$. Parallel agents can explore many useful ideas, but reporting only their best-looking result compounds selection bias. An experiment ledger and fresh confirmatory data are therefore part of scaling research, not clerical overhead.

Stateful tools help, then demand discipline

“When you give an agent a notebook” explains that models and data can load once, allowing a failed downstream cell to be corrected without restarting expensive setup. “Organized & Traceable Outputs” argues for keeping code, plots, and analysis together. A notebook makes evidence easier to inspect only if outputs match the saved code and execution order is recoverable.

A clean restart-and-run test catches hidden state: variables left from deleted cells, changed random seeds, mutated model weights, stale dataframes, and figures generated before a correction. For expensive workloads, small deterministic reference runs and explicit checkpoints can provide a feasible integrity check. A saved image without its data and execution provenance remains weak evidence.

“Security” notes that notebook execution can bypass restrictions enforced only on shell tools. This is a concrete architectural point: policy must cover the actual execution surface, not just one command interface. It is not authorization to bypass those controls. The same principle applies to filesystem access, network calls, and package installation through a kernel.

A critic is another fallible instrument

“Validation & Other Challenges” gives examples of shortcutting, selective reporting, and accepting bugs as discoveries. Critic agents can help inspect these failures, but agreement between agents may reflect shared assumptions or shared model errors. Independent checks should use analytic solutions, reference implementations, randomized negative controls, data provenance, or genuinely separate evidence where possible.

“Ensembling & Parallelization” proposes multiple approaches to open-ended questions. Diversity of search can increase discovery probability, while correlated agents reduce the benefit. Replication by agents using the same code and data is weaker than independent implementation or new data. The essay's “shallow validation debt” describes a workflow advantage of unreviewed results being separable; it does not make those results safe to cite as established knowledge.

“Our open source notebook tool & interpretability task suite” explicitly says the tasks are not formal benchmarks and have not undergone rigorous auditing. Preserve that qualification. The generalizable contribution is a set of workflow hypotheses: stateful tools can improve iteration, organized artifacts can improve review, and verification becomes more valuable as execution becomes cheaper.

Reading route and capability

Read “Developer agents versus experimenter agents,” the notebook sections including “Security,” “Validation,” “Context Engineering,” and the task-suite qualification. You should specify an agent experiment so another person can reconstruct its question, exact inputs, execution, negative controls, conclusion, and unresolved alternatives. Use the local labs as bounded examples of this evidence contract.

Exercises

  1. Why is a passing software test insufficient to validate a scientific conclusion?
  2. For ten independent tests at level $0.01$, find the probability of at least one false positive. Give the Bonferroni per-test level for familywise error at most $0.05$.
  3. Design a critic review that does not merely reread the experimenter's conclusion.
