Run an experiment whose conclusion you can inspect

The local labs are controlled examples supporting the Goodfire reading. They distinguish an analytic construction, a numerical check, and an empirical observation from a trained small model. None is silently substituted for the original paper's experiment.

The core environment already has Python, NumPy, SciPy, PyTorch, and Matplotlib. The HTML course and its mathematics need only a modern browser. Python labs require the prepared software environment, which is a separate requirement from opening the documents. Optional experiments with pretrained large models are described without making downloads a prerequisite for the course.

Start with one small run

Open PowerShell, change to the project folder, and run the first lab:

cd goodfire-tutorials
python docs\learning\labs\run_lab.py --lab relu

The program saves machine-readable measurements under learning/labs/results/ and plots under learning/figures/. Read its printed scope before interpreting the result. Open the corresponding JSON result in a text editor or browser. The lab index explains every experiment, its inputs, its expected checks, and the relevant essays.

To run the complete prepared suite, use:

python docs\learning\labs\run_lab.py --lab all

This command uses generated local data. It does not call a model API, download model weights, or purchase compute. Training labs use intentionally small models, with saved seeds and measured results.

Read code by its scientific contract

Before following individual lines, identify the input variables, model parameters, measured output, and intervention. A tensor shape tells you which axes represent examples, positions, channels, or features. The same numeric array can mean very different things under different axis conventions.

In PyTorch, the forward pass computes outputs from tensors. A gradient tracks a local derivative of a scalar objective with respect to selected tensors. A hook can record an intermediate activation or replace it during a forward pass. An evaluation mode changes certain module behaviors; disabling gradient recording changes bookkeeping. These operations serve different purposes. The small lab implementations name each use explicitly.

State a prediction before running the code, then separate the observed result from your interpretation. If the output disagrees, inspect shapes, labels, preprocessing, and the intervention before inferring a surprising scientific fact. If it agrees, test a counterexample or a held-out condition before generalizing.

What a reproducible result includes

A reproducibility record needs the code version or hash, software versions, random seeds, data construction or data hashes, model configuration, evaluation inputs, and the score definition. A seed alone does not guarantee identical results across every hardware and library version. Numerical tolerances should reflect the computation and the claim.

A training set chooses model parameters. A validation set can choose hyperparameters or analysis settings. A final evaluation set tests a claim after those choices. Repeatedly inspecting the final set while changing the method makes it part of development. Keep a fresh confirmation set when exploratory analysis suggests a new mechanism.

The repository's validation receipts show which checks actually ran. An analytic equality can be checked on many inputs, but finite testing does not prove a universal theorem. Conversely, a theorem about a specified construction does not establish an empirical claim about a frontier language model.

Exercises

  1. Write a prediction for the ReLU lab at a negative input before running it. Identify which saved fields constitute observations and which conclusions require reasoning.
  2. You change the random seed after seeing an unhelpful result and keep only the best run. What evidence is missing from the final report?
  3. Design a record that would let another reader repeat a source-specific intervention. Include the exact location and type of intervention, not just the model name.
